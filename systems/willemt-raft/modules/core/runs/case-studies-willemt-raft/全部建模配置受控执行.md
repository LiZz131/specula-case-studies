# 六种建模配置的受控执行

`spec/base.tla` 的动作公式没有改。受控执行仍用 `spec/base_for_sandtable.tla` 里的 `scr.pc` 和 `seq`。这一轮把 Specula 对 willemt/raft 的六份模型检查配置都换成同一套 `MC_for_sandtable` 模块，各跑 100 条随机轨迹。每条轨迹在 `DepthBound`（TLC level 31，最多 30 步）或更早的死锁处停下，然后全部做受控执行。

| 配置 | 来源 | 与标准配置的差别 |
|---|---|---|
| `MC_for_sandtable.cfg` | `MC.cfg` | 超时 2、请求 1、不丢消息、不快照 |
| `MC_for_sandtable_commit.cfg` | `MC_hunt_commit.cfg` | 超时 5、请求 3、丢消息 3、日志长度 4 |
| `MC_for_sandtable_broadcast.cfg` | `MC_hunt_broadcast.cfg` | 同上，另加快照 2 |
| `MC_for_sandtable_log.cfg` | `MC_hunt_log.cfg` | 超时 4、丢消息 3、快照 1 |
| `MC_for_sandtable_snapshot.cfg` | `MC_hunt_snapshot.cfg` | 超时 4、丢消息 2、快照 2 |
| `MC_for_sandtable_vote.cfg` | `MC_hunt_vote.cfg` | 超时 5、丢消息 2、快照 1，并检查 `TermNeverDecreases` |

`Crash`、`Recover`、`DuplicateMessage` 没有放进 `MCNext`。驱动没有崩溃和恢复命令；WRaft 走 TCP，`duplicate` 只作用于 UDP。配置文件里仍写着原来的 `CrashLimit` 和 `DuplicateLimit`，随机游走不会选这些动作。`LoseMessage` 只在该 TCP 通道上恰好有这一条消息时启用，回放用 `clear src dst`。`AppendEntriesAll` 对应 `raft periodic 200`，不按 `BroadcastLimit` 计数。

轨迹在 `sandtable/build/mount/systems/WRaft-series/SpeculaWRaft/bugs/random/cfgs/<配置>/t001` … `t100`。逐条数字在 `coverage-by-config.json`。

## 适配层修正

`raft_recv_appendentries_response` 先 `raft_set_commit_idx`，再 `raft_send_appendentries`，发出去的 `leader_commit` 是新值。原先 `WireMsg` 读的是动作开始时的 `commitIndex`，跟随者会按过小的 `leaderCommit` 计算提交点。`WireMsg` 增加了提交点参数；成功响应这条分支传入更新后的值。修正之后，一条含 `TakeSnapshot` 的 30 步轨迹可以整段比完。

## 不一致

**任期拒绝，71 条。** 接收者处理 `HandleRequestVoteRequest` 之后，模型里的 `currentTerm` 高于代码。`raft_recv_requestvote`（`raft_server.c:586-591`）在更新任期之前返回：已经有 `current_leader`、请求不是这个 leader 发来的、并且 `timeout_elapsed < election_timeout` 时，直接 `vote_granted = 0`。代码回复了 not granted，序号对应的消息已经投递。标准配置的 100 条没有走到这一步。这和上一轮 t098 是同一处库行为。没有改模型去掩盖它。

**队列比模型多 1 条，7 条**（广播 1、日志 1、快照 5）。最后一次 `compare net-len` 警告，例如代码 12、模型 11。变量比较仍然通过，控制器不中断，轨迹以 `logout` 结束。

**连接断开，1 条。** `log/t027` 在投递 n1 到 n2 的 AppendEntries 时，`check_has_recv_queue` 连续失败，随后 n2 与 n1 的 TCP 连接被关闭。这一步没有执行，n2 的 `commitIdx` 停在 1，模型是 3。这是这次回放的传输中断，不是协议赋值差异。
