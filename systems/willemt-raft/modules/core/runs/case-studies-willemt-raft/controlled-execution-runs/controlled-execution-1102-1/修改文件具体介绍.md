# 这一轮的 wraft 驱动，以及它和 SandTable 的接口

驱动在本轮副本里：

`sandtable/systems/WRaft-series/driver/deps/WRaft.cpp`

生成器把模型的 `pc` 写成控制器命令：

`sandtable/systems/WRaft-series/WRaft/scripts/testcase_generator.py`

控制器二进制没有重编。它只认识下面这些命令，通过 `execute <节点> <文本>` 把 `<文本>` 交给该节点上的 `RaftRepl`，通过 `execute <节点> get <名字>` 取回 `RaftGet` 的字符串。节点名是 `n1`、`n2`、`n3`。

## 驱动多做的事

相对「库自己跑、时钟和网络自己走」的用法，这一份驱动把每一步收成控制器的一条命令。

- 虚拟时钟。`Timeout` 不睡觉。控制器先 `intercept inc_time_ms 2000`，再 `raft periodic 2000`，库的 `raft_periodic` 收到 2000 毫秒。选举超时区间是 `[1000, 2000)`，所以一次就跨过超时。
- 发送开关 `capture_sends`。为真时，库的发送回调才调用 `net->send_to`，字节进入拦截器，按捕获序号排队。为假时回调直接返回 0，字节不进袋子。客户端写入、处理一封请求、打快照这三处会暂时关掉，避免库在同一步里发出公式没有单列的消息。
- 公式要求的回复由驱动补发。处理 AppendEntries 请求之后调用 `raft_send_appendentries_resp`。处理投票请求之后调用 `raft_send_requestvote_resp`。这两次发送发生在 `capture_sends` 重新打开之后，所以回复进入袋子，对应公式里的 `Reply`。装入快照不发回复，公式也只 `Discard` 请求。
- 投票请求到达前的 `vote-mode`。`lease` 把 `current_leader` 设成自己并把 `timeout_elapsed` 清零。`open` 把 `current_leader` 清空。设完就清掉模式，不调用 `raft_periodic`。
- 持久副本。库回调 `persist_term`、`persist_vote`、`log_offer`、`log_poll`、`log_pop` 时，驱动把任期、投票和日志写到 `/tmp/wraft-persist-nX`，`fsync` 之后改名。每条成功的 raft 命令结束时，`sync_retained` 再把快照下标、快照任期、`nextIndex`、`matchIndex`、`votesGranted` 写进同一份文件，不覆盖任期、投票和日志。`log_clear` 没有注册，压缩前缀靠 `log_poll`。
- 崩溃。`raft crash` 先把当前 12 个变量写成 `/tmp/wraft-freeze-nX`，再 `raft_free`。容器和驱动进程还在，`server_down` 为真。之后 `get` 读冻结文件。这不是失败。
- 恢复。`raft recover` 只读持久副本：重建 `raft_server`，按副本重放日志，把角色设成 Follower，`commitIndex` 和 `lastApplied` 设成 0，再按副本恢复 `nextIndex`、`matchIndex` 和已得票。不从刚停掉的内存里拷。
- 条目的值。`v1` 写在 `raft_entry_t.data.buf` 这个指针槽的低位，长度不超过一个指针减一。比较时 `entry_text` 把这些字节读回来，所以日志的样子是 `[(1, 'v1')]`。

## 控制器发给驱动的命令

`RaftRepl` 按第一个词分发。除了 `recover`，服务器已经崩溃时其它词直接失败。

| 命令 | 库调用 | 作用 |
|---|---|---|
| `raft init` | `raft_new`，`raft_set_callbacks`，`raft_add_node` | 清空旧的持久文件和冻结文件，三个节点都是投票节点 |
| `raft periodic 2000` | `raft_periodic(me, 2000)` | 只在 `Timeout` 使用。候选人会提高任期并发投票请求，这些发送会被捕获 |
| `raft vote-mode lease` 或 `open` | 不调用库 | 只记住模式，下一封投票请求到达时用掉 |
| `raft recvfrom nX` | 见下表 | 从拦截器取出 nX 发来的一封，按类型交给库 |
| `raft cli v1` | `raft_recv_entry` | 写入一条日志。调用期间 `capture_sends` 为假 |
| `raft send nX` | `raft_send_appendentries` | 返回 0 或 `RAFT_ERR_NEEDS_SNAPSHOT` 都算成功。后一种会走快照回调，发出 `MSG_SNAP` |
| `raft snapshot` | `raft_begin_snapshot` 然后 `raft_end_snapshot` | 调用期间 `capture_sends` 为假。快照结束时库自己想发的消息不进袋子 |
| `raft crash` | `raft_free` | 写冻结文件，留下持久副本 |
| `raft recover` | `raft_new` 后按副本重放 | 见上面的恢复 |
| `raft statemachine` | 不读库状态 | 打印驱动自己累积的应用字符串，不参加 `compare` |

`recvfrom` 按包前面的类型字分发：

| 类型 | 库函数 | 驱动接着做的事 |
|---|---|---|
| `MSG_AE` | `raft_recv_appendentries` | 捕获关掉，返回后把响应发回，响应进袋子 |
| `MSG_AER` | `raft_recv_appendentries_response` | 捕获关掉。成为领导者时库内部的 AppendEntries 不进袋子 |
| `MSG_RV` | `raft_recv_requestvote` | 先按 `vote-mode` 改 `current_leader`，捕获关掉，返回后把投票响应发回 |
| `MSG_RVR` | `raft_recv_requestvote_response` | 捕获关掉 |
| `MSG_SNAP` | 驱动里的 `raft_recv_installsnapshot` | `raft_begin_load_snapshot`、重新 `raft_add_node`、`raft_end_load_snapshot`。不发响应 |

## 控制器不经过 raft 的命令

这些由控制器和拦截器执行，驱动进程看不到：

| 命令 | 作用 |
|---|---|
| `init 3` | 准备 3 个节点 |
| `execute nX net connectall` | 节点之间建连接 |
| `wait-init 3`、`loop execute nX net isallconnected` | 等到 3 个节点和 6 条连接就绪 |
| `intercept nX inc_time_ms 2000` | 把该节点的虚拟时钟拨快 2000 毫秒 |
| `deliver-unordered nSrc nDst <捕获序号>` | 把这一份捕获交给目的节点的接收队列。投递之后这份捕获不能再投递 |
| `loop intercept nDst check_has_recv_queue nSrc` | 等到这一份已经进了接收队列 |
| `drop-unordered nSrc nDst <捕获序号>` | 丢掉这一份，并把该捕获序号标成已丢 |
| `duplicate-unordered nSrc nDst <捕获序号>` | 再入队一份。新份使用新的捕获序号 |
| `compare variable` | 把上一条 `get` 的返回值和上一条 `# variable` 的模型值比较。不等就断言退出 |
| `compare net-len` | 比较捕获条数和模型消息袋大小。不等只警告 |
| `status` | 一步结束 |

公式序号和捕获序号从 1 起相同。每复制一封，后面新发出的捕获序号都加 1。所以 `pc` 末尾的序号和 `deliver-unordered` 上的序号会不一样。丢失时优先丢掉复制出来的那份，留下原来的那份还可以投递。

## 库回调进驱动

`raft_set_callbacks` 注册的是这些。驱动用它们把库的副作用接成文件或网络字节。

| 回调 | 驱动做什么 |
|---|---|
| `send_requestvote` | `capture_sends` 为真时，把请求打成 `MSG_RV`，`net->send_to` |
| `send_appendentries` | 同样，类型是 `MSG_AE`。条目按结构体逐个拷进缓冲区 |
| `send_snapshot` | 类型是 `MSG_SNAP`，只带任期和快照的最后下标、最后任期 |
| `applylog` | 把条目文本追加到驱动自己的 `state_machine` 字符串。不参加比较 |
| `persist_term` | 写任期和投票，除非正在从副本重放 |
| `persist_vote` | 写投票 |
| `log_offer` | 日志末尾加一条，并写盘 |
| `log_poll` | 删掉日志第一条，并写盘 |
| `log_pop` | 删掉日志最后一条，并写盘 |
| `log` | `FLAGS_detail` 时把库的日志行打到标准输出 |

`log_clear`、成员变更和 `node_has_sufficient_logs` 没有接到会改状态的实现。`log_clear` 在回调表里是空指针。

## `get` 的返回值从哪来

`RaftGet` 的键就是 `compare` 用的名字。`commitIdx`、`nextIdx`、`matchIdx` 会先改写成 `commitIndex`、`nextIndex`、`matchIndex`。服务器还在时读库内存：

| 名字 | 内存位置 | 格式 |
|---|---|---|
| `commitIndex` | `commit_idx` | 十进制 |
| `currentTerm` | `current_term` | 十进制 |
| `log` | `log_get_at_idx`，从快照下标之后逐条取 | `[(任期, '文本'), ...]` |
| `state` | `state` | `1` / `2` / `3` |
| `lastApplied` | `last_applied_idx` | 十进制 |
| `votedFor` | `voted_for` | `Nil` 或 `n1`/`n2`/`n3` |
| `votesGranted` | 各节点 `raft_node_has_vote_for_me` | `{n1,n2}` |
| `snapshotLastIdx` | `snapshot_last_idx` | 十进制 |
| `snapshotLastTerm` | `snapshot_last_term` | 十进制 |
| `nextIndex` | 各节点 `raft_node_get_next_idx` | `{'n1': 1, 'n2': 2, 'n3': 2}` |
| `matchIndex` | 各节点 `raft_node_get_match_idx` | 同样的字典 |
| `crashed` | 进程还在 | `FALSE` |

`server_down` 时不碰已经 `raft_free` 的内存。`crashed` 固定返回 `TRUE`，其余 11 个读 `/tmp/wraft-freeze-nX`。这份文件是 `raft crash` 当时按同样的格式写的。

六条典型轨迹里这些值的具体变化在 `典型trace解读.md`。
